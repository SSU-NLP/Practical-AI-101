## 도입부

- **RAG가 뭔가요? — 오픈북 시험 비유**: 암기 시험(모델 단독) → 오픈북 시험(근거를 쥐여 줌).
  Retrieval(찾아서) · Augmented(건네주고) · Generation(근거 보며 답한다)
- 오늘 쓰는 환경 안내 (위 표)
- 오늘의 목표 4가지 / **최종 목표 미리 보기**:
  ```python
  ask_rag("서울도서관 자원봉사자는 몇 명 뽑아?")
  # → "총 5명 내외를 선발하며, 만 18세 이상 서울시민이 대상입니다. (근거: ... 모집 공고)"
  ```

## 1. 환경 설정 (2차 복습)

- 라이브러리 설치: `openai` + `faiss-cpu`
- API 키 입력 · `client` 생성 — **2차 코드 그대로 재사용** (Colab 🔑 보안 비밀 자동 로드 포함)
- **공지 데이터 내려받기** — GitHub raw URL에서 JSONL 로드, `title`/`content`/`published_at`/`source_url` 소개.
  데모에 쓸 자원봉사자 공지를 출력해서 미리 읽게 한다
- **전처리** — 본문이 사실상 비어 있는 공지(정보가 전부 첨부 PDF·포스터에 있는 것) 걸러내기.
  상투구와 제목 반복을 걷어낸 실질 내용이 150자 미만이면 제외 → 11건 제외, 123건 유지

> 💡 환각을 체험하려면 API 호출이 먼저 가능해야 하므로, 문제 제기보다 환경 설정을 앞에 둔다.

## 2. 문제 제기 — 모델은 모르는 것도 지어낸다 (환각)

- 공지를 **주지 않고** 데모 질문 → 1절에서 읽은 정답과 대조
- 모델의 두 가지 반응 모두 실격임을 확인
  - 그럴듯한 인원·마감일을 자신 있게 지어냄 → 근거 없음
  - "확인이 필요합니다" → 정직하지만 **챗봇으로서 쓸모없음**
- ⭐ 오늘의 문제 정의: **모델이 본 적 없는 문서에 대해, 지어내지 않고 출처를 밝히며 답하게 만들자**

## 3. 가장 단순한 해결책 — 문서를 통째로 프롬프트에 넣기

- 123건 전부는 20만 자라 못 넣으므로, **정답 공지를 포함한 10건**만 넣고 같은 질문 → 정확히 답함
- 이것이 RAG의 본질 전부. 그런데 **입력 토큰 수**(10건에 이미 만 단위)를 보면 문제가 보인다

| 문제 | 설명 |
|---|---|
| 길이 한계 | 전부 넣으면 20만 자 — 컨텍스트 초과 |
| 비용 | 질문 하나마다 문서 전체 요금 |
| 정확도 | 관련 없는 내용이 섞일수록 핵심을 놓침 |

- 결정적으로 **정답 문서를 사람이 골라 넣었다** → 그게 가능하면 챗봇이 필요 없다
- → **"관련 있는 문서를 자동으로 골라 넣자"** → '관련 있다'를 어떻게 계산? (다음 절)

## 4. 임베딩 — 문장을 좌표로 (1차 연결)

- 1차에서 직접 학습시킨 임베딩을, 오늘은 **학습 완료된 모델**로 받아 쓴다 (단어 → **문장 전체**)
- 정규화 후 **내적 = 코사인 유사도**
- 실습: "몇 명 모집?" vs "선발 인원이 어떻게 되죠?" vs "점심 메뉴 추천"
  → 겹치는 단어가 없어도 앞의 둘이 가깝다
- 🎬 **시각 자료: 임베딩 공간** — 의미가 비슷하면 좌표가 가까이 모인다
- 확인 실습: 문장을 바꿔 유사도 비교 (동의어 질문 / 같은 단어 다른 의미)

## 5. 문서 쪼개기 — 청킹(Chunking)

- 1만 자짜리 축제 안내문을 벡터 하나에 담으면 축제 수십 개가 뭉개진다 → **조각 단위로 검색**
- `split_text()` 를 **직접 구현**하며 세 가지 원칙을 배운다

| 원칙 | 이유 |
|---|---|
| 크기 상한 (900자) | 한 조각 = 한 주제에 가깝게 |
| 오버랩 (120자) | 경계에서 문장이 잘려도 다음 조각이 물고 시작 |
| 제목 접두어 | 조각만 봐도 어느 공지인지 알아야 검색·출처 표시가 된다 |

- 자를 위치는 **줄바꿈 우선**(`rfind("\n", ...)`)으로 찾아 문장 한가운데를 피한다
- 확인 실습: 가장 긴 공지의 **첫 조각 끝 120자 vs 둘째 조각 앞 120자**를 나란히 출력 →
  같은 내용이 겹쳐 보이는 것을 눈으로 확인. `CHUNK_SIZE=300, OVERLAP=0` 으로 바꿔 실험

## 6. FAISS — 벡터 DB에 청크를 넣고 검색하기

| 코드 | 하는 일 |
|---|---|
| `faiss.IndexFlatIP(차원수)` | 빈 인덱스 생성. `IP`=내적 → 정규화 벡터에선 코사인 유사도 |
| `index.add(벡터들)` | 청크 벡터 저장 |
| `index.search(질문벡터, k)` | 상위 k개의 (점수, 번호) 반환 |

- ① 인덱싱(한 번만): 청크 300개 임베딩 → 인덱스에 저장
- ② `search(question, k)` 정의 → LLM 없이 **순수한 '찾기'** 테스트.
  3절에서 사람이 골랐던 문서를 이제 **컴퓨터가 알아서 찾는다**
- 📖 [참고] `Flat`은 전수조사. 수백만 개면 IVF·HNSW 근사 인덱스로. Chroma·Pinecone도 같은 원리
- 확인 실습: 여러 질문의 1등 공지가 맞는지 눈으로 검증 +
  **공지에 없는 질문도 뭔가는 뽑혀 나온다** → 다음 절의 "없으면 모른다고 해" 지시로 연결

## 7. 검색 + 생성 = RAG 완성

- 조립: 질문 → `search()` → 청크를 프롬프트에 삽입 → 답변
- 프롬프트 규칙 두 가지: **근거 제한**("공지에 근거해서만, 없으면 모른다고") + **출처 표시**(제목·게시일·링크)
- 🎬 **시각 자료: RAG 한 번 왕복**
- **2절과 같은 질문 재도전 → before/after 비교 (수업 하이라이트)**

| | 2절 (문서 없이) | 3절 (통째로) | 7절 (RAG) |
|---|---|---|---|
| 답변 | 지어냄 | 정확 | 정확 + 출처 링크 |
| 문서 선택 | — | **사람이 손으로** | **검색이 자동으로** |
| 입력 토큰 | 적음 | 넣은 문서 전체 | 검색된 k개만 |
| 확장성 | — | 문서가 늘면 한계 | 10배 늘어도 입력은 그대로 |

- 파이프라인 정리:
  ```
  [인덱싱, 한 번만] 공지 → 전처리 → 청킹 → 임베딩 → FAISS 인덱스
  [질문마다]        질문 → 임베딩 → 유사도 검색 → 상위 k개 → 프롬프트 → LLM → 근거 있는 답변
  ```

## 8. 연습문제 🎯

| 문제 | 하는 일 | 할 일 | 핵심 |
|---|---|---|---|
| 1 | 페르소나 기능 추가 (`ask_rag_v2`) | 빈칸 1개 ✏️ | **RAG = 검색 결과를 프롬프트에 넣는 것** |
| 2 | "모르면 모른다"는 안내원 | 프롬프트 실험 👀 | 환각을 막는 행동 규칙 |
| 3 | 내 문서로 나만의 챗봇 | 문서 교체 ✏️ | 문서만 갈아 끼우면 파이프라인은 그대로 |

- **문제 1**: 빈칸은 `context`를 프롬프트에 넣는 한 줄.
  ⭐ "RAG는 모델을 바꾸는 기술이 아니라 프롬프트에 근거를 넣어 주는 기술" — 채우기 전/후 비교도 권장
- **문제 2**: 규칙 ①근거 제한 ②없으면 "서울문화포털에서 직접 확인해 주세요" ③게시일·링크 표시
  (지난 공고일 수 있음을 알리는 것까지). **공지에 없는 질문**("따릉이 요금")에서 지어내지 않는지가 채점 포인트
- **문제 3**: `MY_DOCS` 에 자기 문서 넣기 → 5~6절 코드 그대로 재실행.
  **문서가 바뀌어도 청킹 → 임베딩 → 인덱싱 코드는 한 글자도 안 바뀐다**

## 정리

- **이번 주에 배운 것**: 환각 / RAG / 전처리 / 임베딩 / 코사인 유사도 / 청킹 / FAISS / 근거 제한 프롬프트
- **반드시 기억할 세 가지**
  1. 모델은 모르는 것도 지어낸다 → 근거를 쥐여 주는 RAG가 필요하다
  2. RAG의 품질은 **검색의 품질**이 결정한다 — 생성은 검색을 못 이긴다
  3. RAG = 검색 결과를 프롬프트에 넣는 것 — 2차의 `messages` 응용일 뿐
- **3주 회고**: 1차(임베딩·텐서 연산) + 2차(API·messages·프롬프트) → 3차에서 하나의 파이프라인으로
- **추가 학습 과제**: 근사 검색 인덱스(IVF·HNSW), 하이브리드 검색(BM25), 리랭킹,
  쿼리 재작성, RAG + 에이전트

## 확정된 변경 사항

초안(1~10절 구성)에서 다음을 반영해 현재 구성(1~8절)으로 확정했다.

1. **에이전트 섹션 삭제** — RAG에만 집중. (2차 함수 호출과의 연결은 '추가 학습 과제'에서 키워드로만 언급)
2. **"RAG가 틀리는 경우" · "검색 성능 올리기" 삭제** — `k` 조절, 오버랩 튜닝, 쿼리 재작성, 리랭킹은
   대규모 벤치마크 숫자로나 드러나는 효과라 90분 실습에서 눈에 보이는 개선을 만들기 어렵다.
   같은 이유로 리랭킹 빈칸 문제는 **RAG 조립 빈칸**으로 교체.
3. **환경 설정을 1절로** — 환각 체험 자체가 API 호출이므로 문제 제기보다 앞서야 한다.
4. **문서를 직접 쓰지 않고 실제 코퍼스 사용** — 최종적으로 **서울문화포털 공지 크롤링 데이터**.
   (검토했다가 뺀 후보는 아래 참고)
5. **미니 벡터 스토어(numpy) → FAISS** — 실제 벡터 DB를 쓰는 구성으로.
6. **청킹을 미리 해두지 않고 노트북에서 코드로 수행** — 5절이 청킹을 가르치는 자리인데
   완성된 `chunks.jsonl` 을 읽기만 하면 정작 배울 것(크기·오버랩·제목)이 사라진다.
   따라서 노트북은 `documents.jsonl` 만 읽고 `split_text()` 로 직접 자른다.
